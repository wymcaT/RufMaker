# RufMaker 当前优化评估（2026-10-28）

本文保留评估时的发现。后续五类优化已本地实施，结果与验证边界见[阶段记录](OPTIMIZATION-STAGE-2026-10-28.md)和[使用说明](../performance-and-saving.md)。

评估基线为本机 `main / a0491ba` 加当前未提交功能。不是仅检查 GitHub 上的 2.4.0；本机已有组事件、预设参数控制等后续修改。本轮没有推送或 Release。

原生 WinForms 编辑器、Node 工程生成、GameMaker 8.2 运行器的分工符合产品目标。当前最值得投入的是保存完整性、预览缓存和两端一致性。现有测量不足以支持更换 UI 框架或重写引擎。

## 已确认的问题与处理顺序

### 1. 高优先：保存失败可能留下两份不一致的数据

- 入口：`studio/project.mjs` 的 `syncToGame()`，约第 233～305 行。
- 已有单文件 `atomicWrite()`，但整个工程更新不是事务。音乐存在性检查在写入一批脚本之后，而 `rufmaker.json` 在最后写入。
- **隔离复现成立：** 将变量表达式从 `10` 改为 `20`，同时指定不存在的歌曲，保存报“工程音乐不存在”。此时 `rf_global_step.gml` 已变更，工程 JSON 仍保存 `10`。这是失败路径中的实际不一致，不是已发生用户资料损坏的推测。
- 建议先完成资源检查和代码生成，再分阶段提交。引入生成清单/修订号和中断恢复，让工程数据保存状态与 GM 同步状态分别可见。出错时保留可编辑内容和上一个完整生成版本。
- `studio/bridge.mjs` 的 `loadProject()` 会同步写入，桌面加载也会保存。后续项目迁移应在首次改写前保留版本化备份，并记录迁移版本。

### 2. 高优先：过时的渲染请求仍会显示

- 入口：`desktop/EditorCanvas.cs` 的 `QueueRender()`，约第 72～85 行。
- 当前只允许一个渲染任务运行，会合并为最新待处理请求；没有无限队列。但任务完成后仍无条件执行 `image=next`，没有检查请求序号、场景和当前帧是否仍匹配。
- 快速拖动或换场景时，已失效的画面会暂时提交，当前游标和旧画面可能对不上；旧任务还会继续跑完，拖延新请求。此项由源码确认，本轮没有控制用户桌面复现。
- 建议只提交仍匹配的结果，释放废弃位图；在模拟分段边界检查请求取消。异常目前仅写 `Debug.WriteLine`，发布版应提供可定位的日志和非模态状态提示。

### 3. 最大性能收益：避免每次编辑都从头重建弹幕历史

- 链路：`MainForm.MarkChanged()` → `StageCanvas.SceneChanged()` → 新场景快照 → `PreviewCache.ClearHistory()` → 新 `BulletWorld`。
- 当前改名称等操作也会走这条链，数值拖动期间仍会反复使模拟历史失效。右栏控件复用已经有效，下一步不应只继续围绕右栏重建做优化。
- `BulletWorld.Seek()` 每 200 帧留一个检查点，只保留最近 8 个。50 FPS 下只覆盖最近约 32 秒；远距离倒拖可能重新从第 0 帧演算。
- **隔离测量：** 12 发/5 帧、寿命 100 帧、240 颗存活弹幕，定位到第 6000 帧约 **892 ms**；连续前进一帧约 **0.14 ms**。重新创建世界后定位到第 6001 帧约 **891 ms**。从 6001 倒拖至 2000 帧约 **302 ms**，原检查点只剩 4600～6000 帧。
- 建议区分文档修订、模拟修订和绘制修订，按最早受影响时间失效。保留早期稀疏检查点及近期密集检查点，按内存预算淘汰。镜头会影响“出视野销毁”等语义，应纳入依赖判断，不能简单认定所有镜头修改都只影响绘图。

### 4. 中优先：高密度预览会静默省略弹幕

- 入口：`desktop/PreviewRenderer.cs` 第 81、86 行的 `drawn<20000`。
- 简化路径对每个发射器的本体绘制限制 20,000 颗，而生成 GML 没有对应限制，`ObjectStatistics.Capture()` 也按完整数量统计。
- 例如每帧 300 颗、寿命 160 帧，可产生 48,000 颗存活弹幕，预览只遍历前 20,000 颗。统计、预览和实际游戏不再表示同一数量。本轮为源码审查和数量推导，没有运行 48,000 颗的 FPS 测试。
- 建议把性能降级变成明确的预览质量选项，显示省略数量；完整模式保持语义一致。长远收敛简化/高级两条计算路径的取样规则，避免添加一个事件就改变其他发射器的执行路径。

### 5. 中优先：撤销缺少内存预算

- 入口：`MainForm.PushUndo()`、`EditorCore.cs` 的 `UndoEntry`。
- 已有手势合并和相同快照去重；但保留的每步仍是全工程深复制，`undo/redo` 无数量或内存上限。当前编辑器为 x86。
- **隔离测量：** 40 个物件、6400 个键，保留 64 份独立撤销快照约增加 **34.6 MiB 托管内存**。此值不包括位图、原生资源和进程其他内存。
- 建议先加可配置内存预算，再逐步让普通参数/关键帧操作使用差量记录；复杂结构操作保留快照，避免一次重写全部撤销逻辑。

### 6. 中优先：界面可继续添加，保存却在第 201 个物件失败

- 入口：`studio/project.mjs` 第 65 行的 `s.tracks.length > 200`，以及 `MainForm.AddTrack()`。
- **隔离校验成立：** 200 个普通物件被接受，201 个返回笼统的 `Invalid project state`。界面添加入口没有对应数量判断；变量、事件、模板也占用物件数，而非只计算可见轨道。
- 建议先把限制和提示统一，再依据展开规模与实测确定合理预算。不要只随意提高数字，也不要让用户编辑到保存时才知道超限。

## 结构上需要逐步整理的地方

1. **参数定义分散。** `Track` 将所有种类字段放在一个平面结构，C# 默认值、JS 归一化、UI、单位与步长分别维护。`NumericProperty()` 还会从中文显示名映射字段。建议先集中稳定字段 ID、类型、单位、范围、默认值和适用种类，再让 UI 与校验共用；保留现有工程格式做兼容读取。
2. **数学语义有多份实现。** C# 预览、JS 取样和 GML 生成必须一起改。现有跨端数值测试是正确方向，应持续覆盖实际出生、局部时钟、玩家位置、边界帧和倒拖。本轮自机狙对照又找到了一次角度偏移差异，说明只看编译成功不够。
3. **发布流程缺少自动验证门槛。** `.github/workflows/release.yml` 当前主要负责构建、打包和上传。建议至少加入 Node 定向检查与 C# 核心无界面用例；真实 GM 数值检查可先作为本地发布步骤，不要求公开 CI 自动具备完整引擎安装。
4. **本机与远端都显示 2.4.0，但内容不同。** 后续开发构建可附修订号或构建时间，方便用户反馈；正式发布仍按既有版本和更新规则。
